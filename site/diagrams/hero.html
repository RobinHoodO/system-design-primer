Client

Step 1 · Front door

What it is

The person or program making a request.

Its job here

It starts by resolving a name or requesting static content. Dynamic HTTPS traffic continues to the Load Balancer.

Trade-off

Clients depend on DNS; a DNS outage can stop access even when servers are running.

DNS

Step 1 · Front door

What it is

DNS translates a domain name to an IP address.

Its job here

It receives the client lookup and tells the client where to connect. The client can then reach the CDN or Load Balancer.

Examples

  • CloudFlare
  • Route 53

Trade-off

Accessing DNS adds a slight delay, though caching can reduce it.

DNS →

CDN

Step 1 · Front door

What it is

A CDN is a distributed network of proxy servers that serves content close to users.

Its job here

It receives static requests from the Client and serves or fetches files from Object Store. This keeps static work away from Web Server.

Examples

  • CloudFlare

Trade-off

Content can be stale when it changes before its TTL expires.

Content delivery network →

Load Balancer

Step 2 · Spread the load

What it is

A load balancer distributes incoming requests across computing resources.

Its job here

It receives HTTPS traffic from the Client and sends it to Web Server instances. Multiple instances avoid one machine carrying all traffic.

Examples

  • HAProxy
  • NGINX

Trade-off

A load balancer can become a bottleneck if it lacks resources or is configured poorly.

Web Server

Step 2 · Spread the load

What it is

A reverse proxy centralizes internal services behind one public interface.

Its job here

It receives traffic from Load Balancer and routes it to the APIs. It can also serve cached or static content.

Examples

  • NGINX
  • HAProxy

Trade-off

A single reverse proxy is a single point of failure; failover adds complexity.

Worker Service

Step 4 · Async work

What it is

A worker runs jobs outside the request path.

Its job here

It pulls a job from Queue and can update NoSQL or store output in Object Store. This keeps slow work away from the client request.

Examples

  • Celery

Trade-off

Queues can add delays and complexity.

In the primer

Asynchronism / task queues →

Queue

Step 4 · Async work

What it is

A message queue receives, holds, and delivers jobs.

Its job here

Write API Async enqueues work here. Worker Service pulls the next job and processes it in the background.

Examples

  • Redis
  • RabbitMQ
  • Amazon SQS

Trade-off

Queues can add delays and complexity.

Write API Async

Step 3 · App layer

What it is

An application API that accepts work that can finish later.

Its job here

It receives work from Web Server and hands a job to Queue. Worker Service handles that job outside the request.

Trade-off

Queues add delays and complexity for work that would be inexpensive to run synchronously.

Write API

Step 3 · App layer

What it is

An application API that handles writes.

Its job here

It receives write requests from Web Server and sends changes to SQL Write Master–Slave. It can also store files in Object Store.

Trade-off

Loosely coupled services add deployment and operations complexity.

Read API

Step 3 · App layer

What it is

An application API that handles reads.

Its job here

It receives requests from Web Server and checks Memory Cache first. On a miss it reads from SQL Read Replicas.

Trade-off

Loosely coupled services add deployment and operations complexity.

Memory Cache

Step 5 · Fast reads

What it is

An in-memory cache holds key-value data in RAM.

Its job here

Read API checks it first. On a miss, Read API reads from SQL Read Replicas instead. This takes load off the database.

Examples

  • Memcached
  • Redis

Trade-off

Cache invalidation is difficult and adds complexity.

NoSQL

Step 4 · Async work

What it is

A NoSQL database stores data outside the relational model.

Its job here

Worker Service can update it after pulling a job from Queue. It accepts data that does not need the SQL write path.

Examples

  • MongoDB
  • DynamoDB
  • Cassandra

Trade-off

NoSQL systems often trade strong consistency for availability or partition tolerance.

SQL Write Master–Slave

Step 6 · Store and scale data

What it is

A master serves writes and replicates them to slaves.

Its job here

Write API sends writes here. Changes replicate to SQL Read Replicas, which serve read traffic.

Examples

  • MySQL

Trade-off

A master failure before replication can cause data loss.

In the primer

Master-slave replication →

SQL Read Replicas

Step 5 · Fast reads

What it is

Read replicas serve reads after changes are copied from the write master.

Its job here

Read API sends cache misses here. The replicas reduce load on SQL Write Master–Slave.

Examples

  • MySQL

Trade-off

More replicas can mean greater replication lag.

Object Store

Step 6 · Store and scale data

What it is

Object storage keeps static files separately from application servers.

Its job here

CDN serves static files from it, while Write API and Worker Service can store new files there. This removes that content from Web Server storage.

Examples

  • S3

Trade-off

Separate storage increases complexity and requires application changes.

Scaling AWS walkthrough →

Sharding

Step 6 · Store and scale data

What it is

Sharding distributes one data set across databases, each holding a subset.

Its job here

Customers A–M and Customers N–Z show a split by data range. Application logic chooses the shard for each read and write.

Trade-off

You need to update application logic to determine which shard to read and write.

Sharding →

✕

Federation

Step 6 · Store and scale data

What it is

Federation splits databases by function.

Its job here

Customers SQL and Products SQL keep different functions separate. The application chooses the database for each operation.

Trade-off

Joining data from two databases is more complex.
