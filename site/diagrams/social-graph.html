User Graph Service runs breadth-first search and retrieves each adjacent person by ID.

Flow

User Graph Service → Lookup Service → Person Server, repeated for friend IDs.

Flow

User Graph Service → Memory Cache → later graph lookups.

Client

Step 1 · Route the search

What it is

A person’s app or browser starts a friend search.

Its job here

It resolves the site name with DNS. It then sends the search request to the Load Balancer.

Trade-off

The public request uses a REST API.

Load Balancer

Step 1 · Route the search

What it is

A load balancer distributes incoming requests.

Its job here

It receives the client request. It forwards the request to a Web Server.

Trade-off

It adds a separate component before the web layer.

Web Server

Step 1 · Route the search

What it is

The web server runs as a reverse proxy.

Its job here

It receives a request from the Load Balancer. It forwards the request to Query API.

Trade-off

The reverse proxy adds another hop before Query API.

Query API

Step 1 · Route the search

What it is

The public REST API accepts a friend search.

Its job here

Web Server forwards the request here. Query API sends it to User Graph Service.

Trade-off

External communication uses REST, while internal communication can use RPC.

In the primer

Communication › Representational state transfer (REST) →

User Graph Service

Step 2 · Locate the person

What it is

This service finds the shortest path through friend relationships.

Its job here

It receives the search from Query API. It uses Lookup Service, then Person Server, to retrieve people and run BFS.

Trade-off

Searching can take considerable time, so the design can set a time or hop limit.

In the primer

Interview approach › Step 3: Design core components →

✕

Lookup Service

Step 2 · Locate the person

What it is

A lookup maps a person ID to a Person Server.

Its job here

User Graph Service asks it where a person is stored. It identifies the Person Server for the next retrieval.

Trade-off

The graph service may need this lookup again for every adjacent person ID.

In the primer

Application layer › Service Discovery →

✕

Person Server

Step 2 · Locate the person

What it is

A Person Server stores people by person ID.

Its job here

Lookup Service identifies this server. It returns the person and their friend_ids to User Graph Service.

Trade-off

User data must be sharded because all users and relationships do not fit on one machine.

In the primer

Database › Sharding →

✕

Memory Cache

Step 4 · Reuse cached traversals

What it is

A memory cache holds person data and saved BFS traversals.

Its job here

User Graph Service checks or stores complete or partial traversals here. Later searches can reuse them before more Person Server lookups.

Examples

  • Redis
  • Memcached

Trade-off

Cached traversals need an update strategy.

1 · Route the search

The client resolves DNS and sends the search through the load balancer and reverse proxy to Query API.

Query API receives the public friend-search request.

2 · Locate the person

User Graph Service asks Lookup Service which Person Server contains the source person.

The Person Server returns the person and their friend_ids.

3 · Walk the friend graph

User Graph Service runs BFS from the source person through friend IDs.

Each adjacent person can require another Lookup Service and Person Server retrieval.

4 · Reuse cached traversals

Complete or partial BFS traversals can be stored to speed up later searches.

Memory Cache reduces traffic to downstream services for repeated searches.
